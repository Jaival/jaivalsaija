[Invoicely](https://github.com/Jaival/invoicely) is the invoicing app I'm building to learn the full stack: Next.js 16, Postgres, Drizzle and Better Auth. It deploys to Vercel with Neon as the database, so until now it never needed a container. I wanted it to run anywhere with one command, as the first step towards hosting it myself on a VPS. This post covers the local part: a `Dockerfile`, a `compose.yaml` and a CI job that builds the image on every pull request.

## The first image: 3.74 GB

The naive version is one stage: start from `node:24`, add bun, copy the whole repo, install, build and run `next start`. It works, and it's 3.74 GB. It carries every dev dependency, the full Debian image with compilers, the Next.js build cache and the source code, none of which the running server needs.

## Multi-stage: 453 MB

Next.js can trace which files the server actually imports and copy only those into `.next/standalone`, with a small `server.js` to start it. That's one line in `next.config.ts`:

```ts
output: 'standalone',
```

The [Dockerfile](https://github.com/Jaival/invoicely/blob/main/Dockerfile) then has four stages:

- **base**: `node:24-slim` with the bun binary copied in from `oven/bun:1.3.14`. Bun installs, Node runs the build and the server.
- **deps**: `bun install --frozen-lockfile`, so the image gets exactly what's in `bun.lock`.
- **build**: copies the source and runs `bun run build`.
- **runtime**: a fresh `node:24-slim` that gets only `.next/standalone` and `.next/static` from the build stage, and runs `node server.js`.

Nothing from the first three stages ends up in the final image unless it's copied on purpose. The result is 453 MB, of which the app itself is 90 MB; the rest is the slim Debian base and Node. The build stages stay on Debian rather than Alpine so native modules like `sharp` are built for the same C library the runtime uses. Alpine would cut more, and it's a later step.

## Why it runs as non-root

By default a container runs as root. If someone found a way to run code through the app, they'd be root inside the container, one kernel bug away from the host. The Node images ship a `node` user, so the runtime stage copies the files with `--chown=node:node` and switches to it:

```dockerfile
COPY --from=build --chown=node:node /app/.next/standalone ./
COPY --from=build --chown=node:node /app/.next/static ./.next/static
USER node
```

```sh
$ docker run --rm invoicely-web id
uid=1000(node) gid=1000(node) groups=1000(node)
```

The image also has a `HEALTHCHECK` that fetches the home page every 30 seconds, so Docker reports `healthy` only when the server answers.

## No secrets in the image

The app validates its environment at startup, and the build needs it too: Next.js renders pages while building, and Better Auth refuses to load without a secret. Baking a real secret in with `ARG` or `ENV` would leave it in the image for anyone who pulls it. So the build skips env validation and gets a dummy secret on the `RUN` line only:

```dockerfile
RUN SKIP_ENV_VALIDATION=1 \
    BETTER_AUTH_SECRET=build-only-dummy-secret-not-used-at-runtime \
    bun run build
```

That command runs in the build stage, which isn't part of the final image. The real secret comes from `.env` when the container starts. `docker history --no-trunc` on the final image shows no database URL and no secret.

## Migrations before the app

[`compose.yaml`](https://github.com/Jaival/invoicely/blob/main/compose.yaml) has three services, chained with `depends_on` conditions:

```yaml
migrate:
  build:
    context: .
    target: migrate
  depends_on:
    db:
      condition: service_healthy

web:
  build:
    context: .
    target: runtime
  depends_on:
    migrate:
      condition: service_completed_successfully
```

- `db` is Postgres with a named volume and a `pg_isready` healthcheck.
- `migrate` waits until `db` is healthy, runs `bun run db:migrate` once and exits. It's built from its own Dockerfile target, because `drizzle-kit` is a dev dependency that the slim runtime image doesn't have.
- `web` starts only after `migrate` exits with code 0. A failed migration stops the app from starting against a half-migrated database.

From a clean clone it's three steps: `cp .env.example .env`, fill in `BETTER_AUTH_SECRET`, `docker compose up --build`. The app answers on port 3000 with all 14 tables in place.

## The migration that failed without an error

The issue I wrote for this said `postgres:17`. With it, the `migrate` container exited with code 1 and printed almost nothing:

```txt
drizzle-kit migrate
error: script "db:migrate" exited with code 1
```

Running `drizzle-kit` by hand gave the same: exit code 1, no message. Running the migration SQL straight in `psql` showed the real error:

```txt
ERROR: function uuidv7() does not exist
```

The schema uses `uuidv7()` for primary keys, and that function is new in Postgres 18. The CI database already ran 18, so I'd never seen it fail. The fix was `postgres:18`, with one catch: the 18 image keeps its data under `/var/lib/postgresql` instead of `/var/lib/postgresql/data`, so the volume mount moved too. The lesson for me: the local database version should match production, and when a tool fails silently, run the thing it runs yourself.

## Keeping it working

A Dockerfile nobody builds stops working without anyone noticing. So CI now builds both the `runtime` and `migrate` targets on every pull request, with the GitHub Actions layer cache. It pushes nothing yet. Pushing to a registry and deploying to a VPS are the next steps in the [plan](https://github.com/Jaival/invoicely/blob/main/docs/devops/02-docker-vps.md).
